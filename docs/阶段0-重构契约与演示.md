## 共同的数据和接口约定

| 对象 | 数据归属及执行关系 | Web 定位 |
| --- | --- | --- |
| 项目 | `projectId` 是服务、变量集合和图的归属。项目配置保存执行默认值、公共变量和 AI 策略。 | 项目资源为默认页，一级入口为项目资源、执行图、产物、项目配置。 |
| 服务 | 服务及有序地址使用同一修订与事务。地址 ID 在更新时保持。`SERVICE` 传 `{serviceId}`，实际源码由节点选择。 | 卡片可逐条打开或复制地址，服务详情可打开适用的开始节点。 |
| 变量集合 | 以项目下的集合 ID 和 `revision` 标识可冻结的配置。`ENVIRONMENT_SET` 传单个集合 ID。开始节点声明无引用、固定引用或从参数选择。 | 表格与 dotenv 共用草稿。历史用集合修订追溯，敏感值默认掩码。 |
| 执行图 | 每项目一张图。草稿有修订，发布版本不可变，`flowId` 等于开始节点 ID。每流绑定使用稳定节点和字段 ID。确认后保存固定计划、实际目标和输出来源。 | 从开始节点填写参数并预览。从诊断定位节点和字段，从运行记录定位实际来源。 |
| 产物 | `ARTIFACT` 开始参数传 `{artifactId, instanceId?}`，计划按实际目标选定实例。实物身份、所有权、验证状态及清理状态分别记录。业务操作通过 `SERVICE_RESULT` 输出实际服务及逐目标结果。 | 产物页按实际服务、集合、源码、目标、类型和状态筛选，双向定位生产节点和实物所在服务器。 |
| 平台服务器与分组 | `TARGETS` 引用 `serverIds` 和 `groupIds`。构建与部署分别绑定，预览展开组成员，确认后冻结实际服务器 ID。 | 平台维护 SSH、监控与分组。项目中的目标选择、计划和产物详情引用同一个平台实体。 |

项目、服务、集合、图、产物及全局目标在 API 中使用各自的稳定 ID。Web 可从服务卡片带入 `start` 和 `serviceId`，并按开始节点声明将获授权的服务映射到相应 `SERVICE` 字段。`version` 及 `inputs.parameters` 送入预览，参数按字段 ID 索引。确认提交 `expectedConfigurationHash` 和 `idempotencyKey`。确认前计划变化需要重新预览，确认后的运行沿用固定计划并在派发与写入时复核权限和身份。

文件部署消费 `FILE` 或 `DIRECTORY`，Compose 消费 `DOCKER_IMAGE`。普通结果在图声明的类型及依赖范围内传递，临时产物限同一根运行及其子流，独立运行选择可验证的已登记产物。管理端仅构建可省略目标，构建登记可省略服务归属。部署和回滚需要明确的同项目、同服务产物、匹配的实际目标及发布位置。发布身份使用项目、服务、服务器、方式和规范目的地。更换变量集合后，使用同一发布锁与回滚历史。

SQLite 与 PostgreSQL 采用相同的归属、唯一性和事务约束。服务与地址、集合与变量、确认计划与保护引用都在对应事务内保存。对外接口沿用 `/api/v1` 和 `{data}` 响应。资源修改使用 `expectedRevision`，冲突用 `409` 与 `error.details.currentRevision`，引用保护使用 `error.references`。表单行错误用 `error.details.fieldErrors`，运行阻塞用 `error.planIssue`。后端按适用范围返回 `flowId`、`nodeId`、`fieldId`、`entityType`、`entityId`、`code` 和 `message`。

观察者读取授权范围内的资料及脱敏结果。操作员维护授权项目、发布图和运行，目标及凭据使用分别授权。管理员管理平台资源、凭据、项目 AI 策略、审批和产物保留。授权明文读取单独记录审计。Web 依据 API 返回的权限与可见性展示入口，API 和 Worker 在各自阶段执行校验。

## 三条主路径的演示定义

| 主路径 | 通过定义追溯 |
| --- | --- |
| 服务卡片打开地址 | 「星桥商城」的 `storefront` 依次展示联调前端、生产模拟前端和使用说明。三个地址都有稳定 ID，保存顺序与打开操作分别对应服务修订和其地址数据。 |
| 从开始节点选变量并执行 | `target-files` 可选 `test-config` 或 `production-config`。固定 SHA `5038e89acaeb008526d112afc3d68b812e2a10ff` 和 `web-test-group` 保持相同。`load-files` 按 `ENV` 选择仓库文件，节点记录文件值、集合覆盖和实际 Git 提交。 |
| 已登记产物被新运行同机使用 | `target-files` 的 `build-files.webDirectory` 登记在 `test-a` 和 `test-b`。新运行 `deploy-existing` 通过 `{artifactId}` 分别选取并验证原主机实例，发布返回实际服务和逐目标结果。 |

其余入口包括 `manager-build`、`target-image`、`build-and-deploy`、`deploy-compose` 和 `rollback-existing`。`deploy-compose` 复用 `target-image` 的镜像实例，Compose 模板使用同一固定提交。演示地址、主机和仓库使用占位域名，凭据只含示例引用。初始化器和运行模块随后续阶段接入。 [初始化器映射](../examples/refactor-stage0/README.md#初始化器映射)

## 接续开发

阶段 1 从服务与地址事务、工作台服务卡片及平台详情链接入手。阶段 2 可并行实现变量集合及修订、开始节点选择与快照。阶段 3 共享字段目录和诊断结构，先贯通 Git 检出到类型化输出，再接真实产物登记及发布。测试与验收沿现有安排暂缓。
