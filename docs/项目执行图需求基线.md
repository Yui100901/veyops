# 项目执行图系统需求文档

**版本：** V1.1  
**模块：** Project Execution Graph  
**所属产品：** 智能服务器与服务部署管理平台  
**文档状态：** 历史需求基线。当前设计见 [项目执行图需求与实施计划](项目执行图需求与实施计划.md)。

---

# 1. 产品概述

## 1.1 建设目标

执行图系统是整个平台的自动化执行核心，负责项目内代码管理、构建、测试、部署、发布以及服务器运维任务的流程编排。

系统采用项目级统一执行图设计。每个项目只拥有一张执行图，项目内的所有自动化流程统一在这张图中管理。

用户可以通过可视化编辑器创建执行节点，并将节点组织为不同的执行流。

执行流可以从执行图中截取一段连续或连通的流程，形成具有独立输入输出、触发器和执行记录的自动化单元。

仓库和服务不再拥有独立执行图，而是通过关联关系引用项目执行图中的执行流。

## 1.2 核心设计原则

1. 一个项目只有一张逻辑执行图。
2. 一张执行图可以包含多个执行流。
3. 执行图负责统一管理项目内所有自动化流程。
4. 执行流是可以独立运行、触发和复用的执行单元。
5. 执行流可以从执行图中提取。
6. 执行流可以被其他执行流调用。
7. 每个执行流可以配置多个触发器。
8. 服务通过关联关系引用执行流。
9. 仓库作为代码来源，为执行流提供代码输入。
10. 构建产物作为独立资源，在执行流之间传递。
11. 所有执行过程统一由执行引擎调度和管理。

# 2. 核心架构

## 2.1 项目与执行图

Project 与 ExecutionGraph 为一对一关系。

每个项目创建时自动建立一张执行图，所有执行节点、执行流、触发器和执行关系均归属于该执行图。

项目执行图可以包含：

- 前端相关流程。
- 后端相关流程。
- 多个服务的构建流程。
- 多个服务的部署流程。
- 项目级集成测试。
- 完整发布流程。
- 服务器初始化流程。
- 日常运维流程。

不再为不同仓库或服务创建独立执行图。

## 2.2 整体结构

```text
Project
│
├── Repositories
│   ├── Frontend Repository
│   ├── Backend Repository
│   └── Common Repository
│
├── Services
│   ├── Frontend Service
│   ├── Backend Service
│   └── Worker Service
│
├── ExecutionGraph（唯一）
│   │
│   ├── Flow A：前端构建
│   ├── Flow B：前端部署
│   ├── Flow C：后端构建
│   ├── Flow D：后端部署
│   ├── Flow E：集成测试
│   └── Flow F：完整发布
│
├── Environments
│   ├── Development
│   ├── Testing
│   └── Production
│
├── Artifacts
│
└── Execution History
```

## 2.3 执行图与执行流

执行图是项目级自动化流程的统一定义容器。

执行流是执行图中具有独立执行边界的一段流程。

例如：

```text
项目执行图

Checkout
   │
   ▼
Lint
   │
   ▼
Build
   │
   ▼
Test
   │
   ▼
Deploy
   │
   ▼
Health Check
```

可以将其中的 Build → Test 提取为一个独立执行流。

提取后：

```text
Build Flow
   ├── Build
   └── Test
```

这个执行流可以：

- 单独手动运行。
- 配置 Git 触发器。
- 被其他执行流调用。
- 被服务引用。
- 单独查看执行历史。
- 独立配置输入输出。

完整执行图仍然可以通过 Flow Call 节点调用该执行流。

## 2.4 执行单位

所有实际运行的任务都必须通过执行流启动。

执行图本身负责组织和定义流程，不直接作为一个没有明确入口的执行任务。

如果需要执行完整 CI/CD，可以创建一个覆盖完整流程的项目级执行流，例如「完整发布」。

一个项目可以有多个完整执行流，例如：

- 日常开发发布。
- 生产正式发布。
- 全量环境初始化。
- 全项目升级。

这些流程仍然属于同一张执行图。

# 3. 项目资源管理

## 3.1 代码仓库

一个项目可以关联多个 Git 仓库。

仓库配置包括：

- 仓库名称。
- 仓库地址。
- Git 类型。
- 认证凭据。
- 默认分支。
- 仓库访问状态。
- Webhook 配置。
- 分支和 Tag 信息。

不同仓库可以使用不同凭据。

执行流可以关联一个或多个仓库。

## 3.2 服务管理

服务代表项目中可以独立构建、运行或部署的业务组件。

一个项目可以包含多个服务。

服务配置包括：

- 服务名称。
- 服务描述。
- 关联仓库。
- 构建方式。
- 运行方式。
- 部署方式。
- 运行端口。
- 环境变量。
- 健康检查。
- 访问地址。

支持 Monorepo：

- 一个仓库包含多个服务。
- 一个服务由多个仓库共同组成。

## 3.3 服务与执行流关联

服务不拥有独立执行图，通过关联关系引用项目执行图中的执行流。

一个服务可以关联多个执行流。

一个执行流也可以被多个服务复用。

例如：

| 服务 | 执行流 | 用途 |
|---|---|---|
| Frontend | 前端构建 | Build |
| Frontend | 通用 Docker 部署 | Deploy |
| Backend | 后端构建 | Build |
| Backend | 通用 Docker 部署 | Deploy |
| Worker | Worker 构建 | Build |
| Worker | 通用 Docker 部署 | Deploy |

服务与执行流之间需要支持参数映射。

例如，通用 Docker 部署执行流可以接收：

- 构建产物。
- 服务名称。
- 部署环境。
- 目标服务器。
- 容器端口。
- 环境变量。

从而实现一个执行流被多个服务复用。

# 4. 执行图编辑器

## 4.1 基本要求

执行图采用图形化 DAG 编辑器。

编辑器需要支持：

- 节点拖拽。
- 节点连接。
- 节点删除。
- 节点复制。
- 多节点选择。
- 框选节点。
- 节点分组。
- 节点折叠。
- 自动布局。
- 缩放。
- 画布移动。
- 撤销和重做。
- 保存和发布。

编辑器布局建议采用：

- 左侧：节点类型面板。
- 中间：执行图画布。
- 右侧：节点属性配置。
- 顶部：保存、发布、运行、版本等操作。

## 4.2 节点类型

### 基础执行节点

| 节点 | 功能 |
|---|---|
| Git Checkout | 拉取代码 |
| Shell | 执行 Shell 命令 |
| Script | 执行脚本 |
| SSH | 远程执行命令 |
| Docker Build | 构建 Docker 镜像 |
| Docker Run | 启动 Docker 容器 |
| Artifact Upload | 上传构建产物 |
| Artifact Download | 下载构建产物 |
| Test | 执行测试 |
| HTTP Request | HTTP 请求 |
| Notification | 消息通知 |

### 流程控制节点

| 节点 | 功能 |
|---|---|
| Condition | 条件判断 |
| Switch | 多条件分支 |
| Parallel | 并行执行 |
| Join | 多分支汇合 |
| Delay | 延迟执行 |
| Approval | 人工审批 |
| Flow Call | 调用其他执行流 |
| Start | 执行流入口 |
| End | 执行流出口 |

后续支持插件化增加 AI Action、数据库操作和服务器管理节点。

## 4.3 DAG 执行规则

执行图采用有向无环图。

支持：

- 顺序执行。
- 并行执行。
- 条件分支。
- 多分支汇合。
- 节点跳过。
- 失败终止。
- 失败后继续。
- 重试。
- 子执行流调用。

禁止形成节点循环依赖和执行流循环调用。

## 4.4 条件分支

条件分支支持：

- Git Branch。
- Git Tag。
- 执行参数。
- 环境变量。
- 上游节点输出。
- 构建结果。
- 测试结果。
- 自定义表达式。

例如：

```text
判断 Git Branch
    │
    ├── develop → 部署开发环境
    │
    ├── main → 等待审批 → 部署生产环境
    │
    └── 其他 → 仅执行测试
```

Git 触发过滤与执行图条件分支是不同机制：

- 触发过滤决定是否启动执行流。
- 条件分支决定启动后执行哪些节点。

# 5. 执行流管理

## 5.1 创建执行流

用户可以在执行图中框选一段连续或连通的节点，将其提取为独立执行流。

创建过程：

1. 选择节点。
2. 系统分析选中区域。
3. 识别入口和出口。
4. 分析外部依赖。
5. 自动生成输入输出参数候选项。
6. 用户确认执行流名称和配置。
7. 保存执行流。

支持提取包含条件分支、并行和汇合关系的连通子图。

## 5.2 提取操作

提供两种操作：

**提取并替换**

将选中节点提取为独立执行流，并在原流程中插入 Flow Call 节点替代选中区域。

默认采用此方式，避免流程逻辑重复。

**复制为独立执行流**

复制节点及内部连接关系，形成新的执行流，原有流程保持不变。

## 5.3 执行流输入输出

执行流必须具有明确的输入输出定义。

例如：

原流程：

```text
Checkout
   ↓
Build
   ↓
Test
   ↓
Deploy
```

截取：

```text
Build → Test
```

系统识别输入：

- 源代码工作区或源码快照。
- Git Commit。
- 构建参数。
- 环境变量。

系统识别输出：

- 构建产物。
- 测试报告。
- 测试状态。
- 执行结果。

执行流的入口和出口应支持多个端口。

内部节点之间原有的依赖关系必须保留。

## 5.4 执行流独立运行

执行流支持独立启动。

启动时系统根据 Input Schema 自动生成参数配置界面。

用户可以填写：

- 仓库和分支。
- Commit。
- 构建参数。
- 环境。
- 目标服务器。
- 构建产物。
- 自定义变量。

必要参数未提供时禁止启动。

## 5.5 执行流调用

执行流可以被同一张执行图中的其他执行流调用。

通过 Flow Call 节点实现。

支持同步调用：

1. 父执行流启动子执行流。
2. 传递输入参数。
3. 子执行流创建独立执行实例。
4. 父执行流等待子执行流完成。
5. 获取子执行流输出。
6. 父执行流继续运行。

后续支持异步调用。

## 5.6 执行流归属规则

- 每个执行节点在同一个图版本中只能归属于一个可执行执行流。
- 其他执行流通过 Flow Call 引用，不复制节点定义。
- 执行流内部允许多个入口和出口。
- 执行流之间不允许循环调用。
- 执行流修改后产生新的图版本。
- 历史执行实例始终使用启动时确定的版本。

# 6. 触发器系统

## 6.1 基本设计

触发器绑定执行流，而不是直接绑定执行图。

每个执行流可以配置多个触发器。

一个执行流也可以不配置自动触发器，只允许手动运行或被其他执行流调用。

触发器负责判断启动条件，并提供执行流需要的输入参数。

## 6.2 触发器类型

| 类型 | 说明 |
|---|---|
| Manual | 用户手动触发 |
| Git Push | Git 分支提交触发 |
| Pull Request | PR 创建或更新触发 |
| Git Tag | 创建 Tag 触发 |
| Schedule | 定时触发 |
| Webhook | 外部 HTTP 请求触发 |
| API | 通过平台 API 触发 |
| Upstream | 上游执行流完成后触发 |

## 6.3 手动触发

所有执行流默认支持手动运行。

用户可以：

- 选择执行流。
- 输入执行参数。
- 选择仓库和代码版本。
- 选择构建产物。
- 选择部署环境。
- 选择目标服务器。
- 预览执行参数。
- 确认启动。

## 6.4 Git 触发器

Git 触发器支持：

- 指定仓库。
- Push 事件。
- PR 事件。
- Tag 事件。
- 指定分支。
- 分支通配符。
- 排除分支。
- 文件路径过滤。
- PR 目标分支过滤。

例如：

- develop 分支提交后启动开发构建。
- main 分支提交后启动正式构建。
- v* Tag 创建后启动发布流程。

一个项目内多个仓库的触发事件必须准确映射到对应执行流，避免无关仓库的提交触发错误流程。

## 6.5 定时触发器

支持 Cron 表达式和时区配置。

可用于：

- 定时备份。
- 日志清理。
- 定时健康检查。
- 定时服务器维护。

## 6.6 Webhook 和 API 触发器

支持独立入口。

要求：

- 身份认证。
- Token 或签名验证。
- 参数映射。
- 请求来源限制。
- 防重复请求。
- 触发日志。

## 6.7 上游触发器

支持根据其他执行流的完成状态启动当前执行流。

可配置：

- 上游执行流。
- 成功触发。
- 失败触发。
- 无论成功失败均触发。
- 输入输出映射。

上游同步调用与独立事件触发需要区分：

- Flow Call 是父子执行关系。
- Upstream Trigger 是独立的触发关系。

## 6.8 触发器规则

一个执行流可以配置多个触发器。

不同触发器之间采用 OR 关系。

同一个触发器内部的过滤条件默认采用 AND 关系。

触发器必须支持独立启用和停用。

人工审批不属于触发器，而是执行过程中的流程控制节点。

# 7. 仓库与代码版本管理

## 7.1 代码来源

执行流可以关联一个或多个项目仓库。

每个代码来源需要记录：

- Repository ID。
- 仓库地址。
- 分支。
- Commit。
- Tag。
- 检出目录。
- 访问凭据。

## 7.2 多仓库执行

支持在同一执行流中获取多个仓库代码。

例如：

```text
Checkout Frontend
        │
Checkout Backend
        │
Checkout Common
        │
        ▼
     集成构建
```

不同仓库可以并行检出。

## 7.3 Source Snapshot

每次执行涉及的仓库代码版本必须固定。

记录：

- 仓库 ID。
- 分支。
- Commit SHA。
- Tag。
- 实际检出版本。

多仓库项目发布时，需要生成统一 Source Snapshot，确保整个发布过程使用确定的代码版本。

不能在同一次发布过程中无约束地获取不同时间的分支最新代码。

# 8. 构建产物管理

## 8.1 产物类型

支持：

- Docker Image。
- 压缩包。
- 二进制文件。
- 静态资源。
- 自定义文件。
- 外部制品仓库引用。

## 8.2 Artifact 数据

每个产物记录：

- Artifact ID。
- 项目 ID。
- 服务 ID。
- 产物类型。
- 版本。
- 存储位置。
- Digest。
- Checksum。
- 来源执行图版本。
- 来源执行流。
- 来源执行实例。
- Git Commit。
- 创建时间。

## 8.3 产物传递

支持三种方式：

1. 上游执行流自动传递。
2. 用户选择历史构建产物。
3. 指定外部产物地址。

独立部署执行流必须声明构建产物输入。

支持指定历史版本和 Docker Image Digest。

禁止生产部署依赖不稳定的 latest 标签。

## 8.4 构建方式

支持两种构建方式：

**管理侧构建**

在管理端或构建执行器中完成构建，然后将产物传输到目标服务器。

**目标服务器构建**

通过 SSH 在目标服务器拉取代码并构建。

默认采用目标服务器构建。

但构建完成后，应支持将产物持久化到统一存储或制品仓库，以便其他执行流复用。

# 9. 多环境和部署管理

## 9.1 环境配置

项目可以创建多个环境：

- Development。
- Testing。
- Staging。
- Production。
- Custom。

每个环境独立配置：

- 目标服务器。
- 环境变量。
- 服务配置。
- 运行参数。
- 部署路径。
- 访问地址。

## 9.2 服务部署

服务通过执行流完成部署。

部署执行流可以被多个服务复用。

执行时传入：

- Service。
- Artifact。
- Environment。
- Target Servers。
- Deployment Parameters。

## 9.3 部署策略

支持：

- 单服务器部署。
- 多服务器批量部署。
- 顺序部署。
- 并行部署。
- 部署前备份。
- 健康检查。
- 失败回滚。

部署策略由执行流及其输入参数共同决定。

# 10. 执行引擎

## 10.1 执行实例

每次执行流运行都创建一个独立 FlowRun。

记录：

- Run ID。
- Project ID。
- Execution Graph ID。
- Graph Version。
- Flow ID。
- Trigger ID。
- Parent Run ID。
- 输入参数快照。
- Source Snapshot。
- 开始时间。
- 结束时间。
- 执行状态。
- 输出结果。
- 错误信息。

父执行流调用子执行流时，子执行流创建新的 FlowRun，并通过 Parent Run ID 关联。

因此不需要在第一阶段引入额外的 GraphRun 实体。

## 10.2 执行状态

| 状态 | 含义 |
|---|---|
| Pending | 等待执行 |
| Queued | 已进入队列 |
| Running | 执行中 |
| Waiting | 等待审批或外部条件 |
| Success | 成功 |
| Failed | 失败 |
| Cancelled | 已取消 |
| Skipped | 已跳过 |

节点也需要独立记录执行状态。

## 10.3 执行调度

支持：

- DAG 节点调度。
- 并行执行。
- 执行超时。
- 节点重试。
- 执行取消。
- 并发限制。
- 互斥执行。
- 失败处理。
- 子执行流调度。

## 10.4 并发策略

执行流需要支持：

- 允许并发。
- 同一执行流串行执行。
- 取消之前的执行。
- 只保留最新一次执行。
- 限制最大并发数。

对于部署类操作，可以按服务、环境或服务器设置互斥限制，防止同时部署产生冲突。

## 10.5 异常恢复

执行状态必须持久化。

平台重启后：

- 恢复可以安全恢复的执行。
- 检查正在执行的节点。
- 识别中断的外部操作。
- 防止重复执行有副作用的操作。
- 无法安全恢复时明确标记状态，等待人工处理。

# 11. 版本管理

## 11.1 执行图版本

执行图采用版本化管理。

支持：

- 草稿。
- 保存。
- 发布。
- 查看历史版本。
- 比较版本。
- 恢复历史版本。

已发布版本不可原地修改。

## 11.2 执行流版本

执行流定义属于项目执行图的一部分。

每次执行图发布都会生成不可变的完整定义快照，其中包括所有执行流及其节点、边界和参数定义。

执行流的具体版本通过执行图版本与 Flow ID 确定。

## 11.3 引用版本策略

服务引用执行流时支持：

- 跟随最新发布版本。
- 固定指定发布版本。

开发环境可以使用最新发布版本。

生产环境建议固定版本，经过验证后再主动升级。

## 11.4 历史追溯

执行实例必须记录当时使用的：

- 执行图版本。
- 执行流定义。
- 节点配置。
- 输入参数。
- 代码版本。
- 构建产物。

保证历史执行记录不受后续修改影响。

# 15. 核心数据模型

建议采用统一的项目执行图模型。

| 实体 | 职责 |
|---|---|
| Project | 项目 |
| ExecutionGraph | 项目唯一执行图 |
| GraphVersion | 执行图发布版本 |
| GraphNode | 执行节点 |
| GraphEdge | 节点连接关系 |
| ExecutionFlow | 执行流逻辑定义 |
| FlowTrigger | 执行流触发器 |
| Repository | 代码仓库 |
| Service | 项目服务 |
| ServiceSource | 服务与仓库的关联 |
| ServiceFlowBinding | 服务与执行流的关联 |
| SourceSnapshot | 代码版本快照 |
| FlowRun | 执行实例 |
| NodeRun | 节点执行实例 |
| Artifact | 构建产物 |
| Deployment | 部署记录 |

核心关系：

- Project 1:1 ExecutionGraph。
- Project 1:N Repository。
- Project 1:N Service。
- ExecutionGraph 1:N GraphVersion。
- ExecutionGraph 1:N ExecutionFlow。
- ExecutionFlow 1:N FlowTrigger。
- Service N:M ExecutionFlow。
- Service N:M Repository。
- FlowRun 1:N NodeRun。
- FlowRun 1:N Artifact。
- FlowRun 1:N 子 FlowRun（通过 Parent Run ID 关联）。

### 关键约束

1. 一个项目只能有一张逻辑执行图。
2. 仓库和服务不能创建独立执行图。
3. 所有执行流都归属于项目执行图。
4. 所有触发器都归属于执行流。
5. 所有实际执行都必须生成 FlowRun。
6. 所有历史执行都必须绑定不可变的执行图版本。
7. 服务引用执行流使用 ServiceFlowBinding 管理。
8. 执行流之间通过 Flow Call 进行复用。

# 17. 第一阶段验收标准

### 场景一：项目统一执行图

创建一个项目后，系统自动生成唯一执行图。

项目中的仓库、服务均可以在该图中使用执行流，不允许为仓库或服务创建独立执行图。

### 场景二：创建完整 CI/CD

创建一条包含代码拉取、代码检查、构建、测试和部署的完整执行流。

能够手动启动并查看完整执行过程。

### 场景三：提取执行流

从完整流程中选中 Build 和 Test 节点，提取为独立执行流。

原流程通过 Flow Call 调用新执行流，执行结果保持一致。

### 场景四：独立触发

为构建执行流配置 Git Push 触发器。

指定分支提交后能够自动启动。

### 场景五：服务复用

创建多个服务，将它们关联到同一个通用 Docker 部署执行流。

通过不同输入参数实现不同服务部署。

### 场景六：独立部署历史产物

用户能够单独运行部署执行流，选择历史构建产物、环境和目标服务器，完成部署。

### 场景七：多仓库协同

项目包含前端、后端和公共依赖仓库。

项目级执行流可以获取多个仓库代码，固定版本并完成统一构建。

### 场景八：历史版本追溯

修改执行图并发布新版本后，历史执行记录仍然使用原版本配置，能够完整追溯。

# 18. 最终架构定义

本系统最终采用以下结构：

**Project**
- 项目唯一资源管理入口。

**ExecutionGraph**
- 项目唯一执行图。
- 统一管理全部节点、连接关系和执行流。
- 支持分组、折叠和筛选视图。

**ExecutionFlow**
- 从执行图中定义的一段独立流程。
- 具有输入输出。
- 可以单独运行。
- 可以配置多个触发器。
- 可以被其他执行流调用。
- 可以被多个服务引用。

**FlowTrigger**
- 决定执行流何时启动。
- 支持手动、Git、Webhook、API、定时和上游触发。

**FlowRun**
- 每次执行流启动产生的独立实例。
- 记录状态、日志、参数和产物。
- 支持父子执行关系。

**Artifact**
- 独立的构建产物资源。
- 支持不同执行流、服务和环境之间复用。

最终形成：

**一个项目、一张执行图、多个执行流、多个触发器、多个执行实例。**

这一架构统一了 CI/CD、服务发布、服务器初始化和自动化运维的流程管理方式，为后续 AI 驱动的自动化执行提供统一基础。
